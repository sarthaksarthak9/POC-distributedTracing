# Tracing POC: Node.js auto-instrumentation

A sample Node.js service that proves the OpenTelemetry Operator injects tracing without changing
the image, the code or a custom start script

## Summary

**What we did.** We ran a Node.js 21 service with a custom start script on a test Kubernetes
cluster with the OpenTelemetry Operator (v0.160.0, Node.js SDK image 0.78.0), and turned tracing on
with two annotations on its Deployment. The start script echoes, loads a simulated secret and
appends to `NODE_OPTIONS` before starting `node`, as production start scripts do. Traces went to a
local Jaeger standing in for the Tier 2 collector.

**Findings.**

| # | Finding | Evidence |
|---|---|---|
| 1 | Tracing needs no code, image or entry-point change | Same `node:21-alpine` image and start script; the operator added only an init container, a volume and environment variables |
| 2 | A custom start script keeps working | The script's echo and secret step ran, and the secret reached the app (`"secretLoaded": true`) |
| 3 | The agent and the script's own Node flags coexist | `NODE_OPTIONS` held both `--require .../autoinstrumentation.js` and `--max-old-space-size=256` |
| 4 | One request produces one connected trace across a service call | Each `/api/chain` request: 3 spans, about 43 ms, the call to `/api/hello` nested inside it |
| 5 | Traces carry the right labels with no extra setup | `service.name` from the Deployment name; `deployment.environment`, `site` and `k8s.*` (namespace, pod, node) present |
| 6 | Order matters | The `Instrumentation` must exist before the pod starts, or the pod is not instrumented; the deploy steps below apply it first |
| 7 | Readiness probes are traced too | Each probe is a one-span `GET` trace: noise to filter later |
| 8 | A startup warning is harmless | `MetadataLookupWarning` is the SDK finding no cloud provider |
| 9 | An operator that enforces its Deployment removes hand-added tracing | Annotations added with `kubectl patch` were reverted within one 15 s cycle, costing two extra rollouts |
| 10 | Tracing configured through the operator's own spec coexists with it | Steady "in sync", pod traced, 0 restarts: the webhook changes pods only, so the Deployment the operator checks never drifts |

**Not yet tested:** the path from the dev cluster to Tier 2, a real Doppler-based start script,
the start-script cases in the table below that stop tracing, a real third-party operator, and
operators or policies that validate running pods.

| File | What it is |
|---|---|
| `app.js` | API on port 3000: `/api/hello`, and `/api/chain`, which calls `/api/hello` over the Service |
| `entrypoint.sh` | Start script that echoes, loads a simulated secret, appends to `NODE_OPTIONS`, then runs `node` |
| `app.yaml` | Deployment (stock `node:21-alpine`, code from a ConfigMap, tracing annotations) and Service |
| `instrumentation.yaml` | Sends traces to Tier 2 over TLS, `https://10.185.13.105:4319`, labelled `deployment.environment=dev` |
| `tier2-ca.crt` | CA of the Tier 2 aggregator, mounted into the pod by the operator |

No image is built: the code and script are mounted from a ConfigMap generated by
`kustomization.yaml`.

## Does injection break a custom start script?

Some services start with a script that fetches secrets before launching the app. Does the
operator's mutating webhook change that start-up, or break the container's entry point?

**No.** The webhook does not change the image, the entry point, the `command` or the `args`. It
adds an init container, a volume and environment variables to the pod. The start script runs
exactly as before, and `node` loads the agent because it reads `NODE_OPTIONS` at start.

What this POC showed, with `entrypoint.sh` as the custom start script:

- The script ran first and completed its pre-start work: the echo and the simulated secret fetch.
- The secret reached the application (`/api/hello` returns `"secretLoaded": true`).
- The agent's `--require` and the script's own flag were both in `NODE_OPTIONS`, because the
  script appends to it.
- The application started normally and produced traces.

A start script stops tracing only in these cases. They follow from how Node.js reads
`NODE_OPTIONS`; this POC did not test them:

| The start script | Effect | Fix |
|---|---|---|
| Sets `NODE_OPTIONS=...` instead of appending | The agent's `--require` is overwritten; no traces | `export NODE_OPTIONS="${NODE_OPTIONS:+$NODE_OPTIONS }<flags>"` |
| Starts node with a cleared environment (`env -i node ...`) | `NODE_OPTIONS` is dropped; no traces | Pass the environment through |
| Ends in a compiled binary rather than `node` | `NODE_OPTIONS` is ignored; no traces | Needs build-time instrumentation |

Secrets delivered by another injector, such as a Vault agent init container or sidecar, are not
affected: the operator's init container is added beside it.

**Start scripts that use Doppler** (`doppler run -- node ...`) start `node` with the
existing environment plus the secrets, so the agent loads. The one exception: if the service's
Doppler config holds a secret named `NODE_OPTIONS`, Doppler's value replaces the operator's by
default and drops the agent. Either move that value into the Deployment, where the operator
appends to it, or run `doppler run --preserve-env="NODE_OPTIONS" -- node ...`. Confirm the flag
with `doppler run --help` for the installed version.

To check a service's start script before enabling tracing:

```bash
kubectl -n <namespace> exec <pod> -- sh -c 'cat /proc/1/cmdline | tr "\0" " "; echo'
kubectl -n <namespace> exec <pod> -- sh -c 'grep -n "NODE_OPTIONS\|env -i" <start-script>'
```

The service must end up running `node` (process 1 is `node`, or a shell script that starts it),
and the script must not set `NODE_OPTIONS` without its existing value.

## Applications managed by another operator

Some applications are deployed by an operator that checks its Deployment against an expected
configuration and corrects any difference. Does adding tracing conflict with it?

`operator-case/` tests this with a reconciler that stands in for such an operator: every 15
seconds it compares the pod-template annotations of the `managed-app` Deployment with its desired
spec (`desired-deployment.yaml`) and replaces the Deployment on any difference. Real operators
differ in what they compare and how; this models a strict one.

| Case | What we did | Result |
|---|---|---|
| A | Added the tracing annotations to the operator-owned Deployment by hand | **Reverted** within one cycle: the operator saw drift and replaced the Deployment. Two extra rollouts, and the pod ended untraced |
| B | Added the tracing annotations to the operator's desired spec | **Works**: the pod is traced, the operator stays in sync, 0 restarts, and traces arrive |

Why case B causes no conflict: the operator compares the Deployment, and the webhook never
changes the Deployment. The init container, volume and variables exist only on the pods; the
Deployment's own spec has no init container.

So, for an operator-managed service:

- Add the annotations through the operator's configuration (commonly a `podAnnotations` field in
  its custom resource), never on the Deployment it owns.
- If the operator offers no way to set pod annotations, annotation-based tracing is not possible
  for that service without changing the operator's configuration model.
- Check whether the operator, or a policy engine such as Kyverno or Gatekeeper, also validates
  running pods. Such a check could reject or flag the injected init container; this POC does not
  cover it.

During the test, the reconciler was itself updated to pick up the new spec, and for a few cycles
the old and new reconciler pods disagreed and replaced the Deployment in turn. That comes from the
stand-in having no leader election, not from tracing.

To run it (after the main POC is deployed):

```bash
kubectl apply -k operator-case/
kubectl -n tracing-poc logs -f deploy/poc-reconciler
```

For case A, patch `managed-app` with the two annotations and watch the log report drift. For
case B, add them to `operator-case/desired-deployment.yaml` and re-apply.

## Prerequisite

The OpenTelemetry Operator is installed on the cluster (runbook section 5).

## Deploy

Apply the `Instrumentation` first: a pod created before it exists is not instrumented.

```bash
kubectl apply -f namespace.yaml
kubectl -n tracing-poc apply -f instrumentation.yaml
kubectl apply -k .
kubectl -n tracing-poc rollout status deployment/tracing-poc-app
```

## Verify

The pod has the injected init container:

```bash
kubectl -n tracing-poc get pod -l app=tracing-poc-app -o jsonpath='{.items[0].spec.initContainers[*].name}{"\n"}'
```

Expected: `opentelemetry-auto-instrumentation-nodejs`.

The start script ran as normal, and the agent was added to `NODE_OPTIONS`:

```bash
kubectl -n tracing-poc logs deploy/tracing-poc-app -c app
```

Expected:

```text
[entrypoint] starting before the application
[entrypoint] secret loaded
[entrypoint] NODE_OPTIONS= --require /otel-auto-instrumentation-nodejs/autoinstrumentation.js --max-old-space-size=256
[app] listening on 3000
```

Send requests:

```bash
kubectl -n tracing-poc exec deploy/tracing-poc-app -c app -- wget -qO- http://localhost:3000/api/chain
```

Then in Grafana, Explore, datasource **Tempo - On-Prem ICOLO**:

```text
{ resource.service.name = "tracing-poc-app" }
```

Each `/api/chain` request is one trace of three spans: the server span for `/api/chain`, the
client call to `/api/hello`, and the server span for `/api/hello`. One-span traces named `GET` are
the readiness probe.
